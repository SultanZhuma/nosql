4. Модель данных

Узлы: User (userId, name, email), Resource (resourceId, name, resourceType, pricePerNight, capacity, available), Location (locationId, name, city, kind).

(:User)-[:BOOKED {bookingId, checkIn, checkOut, status}]->(:Resource)

(:Resource)-[:LOCATED_IN]->(:Location)

(:Location)-[:NEAR {distanceKm}]->(:Location)

BOOKED направлено от пользователя к ресурсу. LOCATED_IN связывает ресурс с местом. NEAR связывает локации; для двустороннего поиска в тестовых данных заведены две направленные связи.

5. Создание данных

Скрипт 02_seed_data.cypher создаёт 6 пользователей, 8 ресурсов и 5 локаций — 19 узлов. Также создаются 8 бронирований, 8 связей размещения и 8 связей соседства, всего 24 отношения.

6. Запросы Cypher

Q01. Простой MATCH

MATCH (u:User) RETURN u.userId, u.name ORDER BY u.name;

Q02. Фильтрация

MATCH (r:Resource) WHERE r.available = true AND r.pricePerNight <= 40000 RETURN r.name, r.pricePerNight ORDER BY r.pricePerNight;

Q03. Сортировка и LIMIT

MATCH (r:Resource) WHERE r.available = true RETURN r.name, r.pricePerNight ORDER BY r.pricePerNight LIMIT 3;

Q04. Поиск бронирований

MATCH (u:User {userId:'U001'})-[b:BOOKED]->(r:Resource) RETURN u.name, b.bookingId, b.status, r.name;

Q05. Двухшаговый обход

MATCH (u:User {userId:'U001'})-[:BOOKED]->(r:Resource)-[:LOCATED_IN]->(l:Location) RETURN u.name, r.name, l.name;

Q06. Обход переменной длины

MATCH (s:Location {locationId:'L001'})-[:NEAR*1..2]->(l:Location) WHERE l <> s RETURN DISTINCT l.name, l.city;

Q07. Агрегирование

MATCH (u:User) OPTIONAL MATCH (u)-[b:BOOKED]->(:Resource) RETURN u.name, count(b) AS bookings ORDER BY bookings DESC;

Q08. Альтернативные ресурсы

MATCH (base:Location {locationId:'L001'})-[:NEAR*1..2]->(near:Location) MATCH (r:Resource)-[:LOCATED_IN]->(near) WHERE r.available = true RETURN DISTINCT r.name, r.pricePerNight, near.name ORDER BY r.pricePerNight;

7. Изменение и безопасное удаление

Сначала изменяется available у ресурса R008 и проверяется результат. Перед удалением связи B007 выполняется MATCH с RETURN. После подтверждения удаляется только эта связь, а контрольный MATCH должен вернуть 0 строк.

MATCH (r:Resource {resourceId:'R008'}) SET r.available=false RETURN r;

MATCH (u:User {userId:'U006'})-[b:BOOKED {bookingId:'B007'}]->(r:Resource {resourceId:'R008'}) RETURN u,b,r;

MATCH (u:User {userId:'U006'})-[b:BOOKED {bookingId:'B007'}]->(r:Resource {resourceId:'R008'}) DELETE b;

MATCH (n) RETURN labels(n) AS labels, count(*) AS qty ORDER BY labels;

9. Сравнение с документной моделью

Neo4j удобна, когда запросы проходят по цепочкам пользователь → бронирование → ресурс → локация → соседняя локация. Документная модель подходит для автономных карточек, но обходы через списки ID требуют дополнительной логики и могут усложнить согласованное обновление связей.

10. Ограничения и масштабирование

Необходимо использовать уникальные идентификаторы, MERGE для повторной загрузки и ограниченную глубину обхода. При росте графа следует проверять планы запросов через EXPLAIN/PROFILE и оценивать индексы и распределение связей.

11. Ответы на контрольные вопросы

Что такое property graph? Граф из узлов с метками и свойствами и отношений с типами, направлениями и возможными свойствами.

Чем узел отличается от отношения и свойства? Узел — сущность, отношение — связь сущностей, свойство — атрибут.

Для чего нужны labels? Для классификации узлов и поиска объектов определённого типа.

CREATE и MERGE? CREATE всегда создаёт элемент; MERGE ищет совпадение и создаёт его, если оно отсутствует.

Как работает MATCH? Описывает графовый шаблон из узлов и отношений.

Почему важно направление связи? Оно отражает смысл отношения и делает запросы однозначными.

Когда атрибут становится узлом? Когда это самостоятельный объект, участвующий в других связях.

Что показывает двухшаговый обход? Путь от пользователя через ресурс к локации.

Зачем ограничивать глубину обхода? Чтобы избежать неоправданно дорогого поиска по большой части графа.

Почему графовая модель полезна? Она естественно выражает запросы, зависящие от цепочек отношений.
